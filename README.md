# sakimawari（先回り）

資料を相手に出す前に、「その相手は、どこで、どんな質問をしてくるか」を洗い出し、**資料の直し方**と**本番での答えの準備**まで提案する、Claude Code 用のスキルです。Microsoft 365 Copilot のエージェント用の版も付いています。

> **ステータス: ベータ版（0.1.0）**
> 作者が作った資料での検査はしましたが、**実際に上司や聴衆から出た質問での評価は、まだ行っていません。** 見落としを減らす補助として使ってください。質問の網羅は、保証しません。

English: [README.en.md](README.en.md)

## 何のためのものか

資料を作った本人は、流れが良いと思い込みやすいものです。理由は、本人の頭の中にだけある前提が、読み手には見えないからです。質問されて初めて、穴に気づきます。

sakimawari は、資料を別の視点で読み直して、質問が出る場所を、出す前に見つけます。質問を並べて終わりにはせず、次の3つをセットで返します。

- **原文の引用**: どの一節から、その質問が出るのか
- **資料の直し方**: 直した文の案。資料にない事実が要る所は、【ここに〇〇】という枠にする
- **答えの準備**: 直さずに本番で聞かれたとき、何を軸に答えるか

## できること、できないこと

できること:

- 報告、提案、企画、承認依頼などの資料の、論理、構造、抜けの点検
- 質問ごとの、重さ（高・中・低）と、どの視点で出た疑問かの表示
- 資料の外の知識が要る質問の、推測としての分離
- 本番前に調べておくことの一覧

できないこと:

- 言い回しや誤字の推敲（別のスキルの仕事です）
- 資料の外の事実の確認（資料にない数字や出典は、作りません）
- 質問の網羅の保証
- コードや設定の確認

## 出力の例

資料（架空）:

> 来月から、社内勉強会を月1回開催したい。参加者の満足度が高く、生産性が上がるためである。

出力（抜粋）:

````markdown
想定した相手: 相手の情報がないため、一般的な聞き手を想定した

## 全体の見取り図

提案の理由が一文だけで、その中の「生産性が上がる」に根拠がない。質問は、この一文に集まる。

| # | 想定質問 | 位置 | 重さ | 視点 |
|---|---|---|---|---|
| Q1 | 生産性が上がるって、どうしてわかる？ | 本文 | 高 | 理由の検査 |

## 1. 資料の中で確認できた穴

### Q1. 「生産性が上がるって、どうしてわかる？」

#### 原文
> 「参加者の満足度が高く、生産性が上がるためである」（本文）

#### どこが引っかかるか
この文は、満足度が高いことを理由に、生産性が上がると言っています。しかし、満足度が高いと生産性が上がる、というつながりは書かれていません。

#### 直し方
> 元：「参加者の満足度が高く、生産性が上がるためである」
>
> 案：「参加者の満足度が高く、【ここに生産性が上がると言える根拠】ためである」

#### 答えの準備
満足度の結果を軸に答えます。生産性との関係は、これから測る、と正直に答えます。測り方は要確認です。

#### 勧めと重さ
資料を直します。開催の理由そのものだからです。
型: 飛躍／重さ: 高（開催の理由そのものだから）／視点: 理由の検査
````

## インストール

### Claude Code

```bash
git clone https://github.com/kiyoshiw0128-web/sakimawari.git
mkdir -p ~/.claude/skills
cp -R sakimawari/skills/sakimawari ~/.claude/skills/sakimawari
```

Claude Code を新しく起動すると、スキルが使えます。

### Microsoft 365 Copilot（エージェント）

Copilot のエージェントビルダーで、カスタムスキルを使う場合の手順です。

前提（Microsoft の資料による）:

- カスタムスキルは、プレビュー機能です。Microsoft Frontier プログラムに登録された組織だけが使えます。
- Microsoft Purview の情報バリアを使うテナントでは、使えません。
- 現時点では、スキルと「埋め込みファイル」を、同じエージェントで併用できません。

手順:

1. スキルの ZIP を作ります。

   ```bash
   python3 scripts/build_copilot_zip.py
   ```

   `dist/sakimawari.zip` ができます。

2. エージェントを新しく作り、「指示」欄に、[`copilot/エージェント指示文.md`](copilot/エージェント指示文.md) の中身を貼ります。
3. 「スキル」の「追加」から、`dist/sakimawari.zip` を、解凍せずにアップロードします。

詳しくは、[`copilot/登録手順.md`](copilot/登録手順.md)。Copilot がスキルの補足資料をどこまで読むかを調べる方法は、[`copilot/読み込み確認/手順.md`](copilot/読み込み確認/手順.md) にあります。

## 使い方

資料を貼るか、添付して、次のように頼みます。

- 「想定質問を出して」
- 「突っ込まれそうなところを教えて」
- 「出す前にチェックして」
- `/sakimawari`

相手の情報があれば、1行で添えます。

```
相手: 部長、案件は初見、コストを気にする
```

なくても動きます。その場合は、一般的な聞き手を想定した、と出力の冒頭に書きます。

## 仕組み（要約）

資料の主張を、「覆されうる推論」として扱います。**穴とは、覆される条件を検討した跡がない箇所**で、**想定質問とは、その覆される条件を尋ねるもの**です。

1. 主張を抜き出し、Toulmin の6要素（主張、根拠、論拠、裏づけ、限定、反証への対応）に分けて、欠けを探します。
2. 次の5つの視点で、資料を読み直します: 文ごとの疑問、理由の検査、役割ごとの視点、失敗の想像、言葉の曖昧さ。
3. 見つけた欠けを、16の型に当てはめ、質問の形にします。
4. 資料の中に答えがあれば、質問にしません。
5. 重さを付け、「答えられなくても、相手の判断も納得も変わらないか」で絞ります（出しすぎない）。
6. 質問ごとに、資料の直し方と、答えの準備を添えます。

詳しい理論と、各項目の根拠（論文）、**根拠の強さの違い**は、[`docs/theory.md`](docs/theory.md) にあります。

## 評価

作者が作った資料22件で、スキルを独立した実行で試しました。

- 仕込んだ穴は、ほぼ見つけました（確認用の資料を含めて、本体の質問として 155/162）。
- 穴のないお知らせや議事録での、質問の出しすぎは、ほぼなくなりました。
- 視点を足したことによる、穴の発見の増加は、小さいものでした（数%）。

詳しくは、[`evals/結果_2026-10-21.md`](evals/結果_2026-10-21.md)。検査の一式（資料、正解、スクリプト）も、[`evals/`](evals/) にあります。

## 既知の限界

- 資料は、作者が作りました。**実際の質問での評価は、していません。**
- 論文の根拠は、ニュース記事、要求仕様書、学生の問題など、仕事の資料とは別の対象で得られたものが多いです。確認の程度は、`docs/theory.md` の第11章に書きました。
- 弱いモデルでは、図の長さや引用の正確さが崩れやすくなります。
- Copilot 版は、Claude 版より、性能が下がることがあります。Copilot の動作は、実機で確かめる必要があります。
- 16の型は、仮説です。網羅は保証しません。

```bash

```
